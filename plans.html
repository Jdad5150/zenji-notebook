Zenji Notebook — Roadmap

v0.5.0 Zig 0.16.0

Architecture

The Python kernel runs as a persistent subprocess. worker.py is embedded in the binary at compile time, written to /tmp on first kernel start, and kept alive between cells so variables persist across executions. Communication is newline-delimited JSON — one command line in, one response line back. 

Browser (SvelteKit — served as static files)
    │
    │  HTTP REST
    ▼
Zig Server Process
    ├── httpz HTTP server
    ├── PythonKernel ──► worker.py subprocess  (stdin/stdout JSON)
    └── Notebook I/O  (reads/writes .znb on disk)

Execution flow: browser sends POST /api/execute { path, cell_id } → server reads cell source from .znb → sends JSON command to worker stdin → reads JSON response (stdout, stderr, base64 figures) → writes text outputs inline to .znb, saves figures to the sidecar directory → returns updated cell JSON.

The .znb file is the source of truth. On first launch the frontend shows the environment picker; the selection is saved to .zenji.json and the kernel is spawned automatically on subsequent starts.

.znb Format

.znb is a compact binary notebook format. Image outputs are not stored in the file — they live in a sidecar directory .{notebook_name}/ and the .znb stores only an image_ref path fragment.

On-disk layout

my_analysis.znb       — source of truth: code, structure, text outputs
.my_analysis/         — execution cache: PNG artifacts
    {cell_id}/
        0.png
        1.png

The sidecar is ephemeral. rm -rf .my_analysis/ clears all figure outputs; re-running cells recreates them. Figures survive server restarts — re-opening a notebook shows the last run's plots without re-executing anything.

Binary layout

[NOTEBOOK HEADER]
magic:         u8[5]   "ZENJI"
version:       u8      (currently 1)
cell_count:    u32
next_cell_id:  u32     monotonic counter — never reused
kernel_type:   u8      0=python 1=julia 2=r 3=mojo

[CELL]  × cell_count
cell_type:       u8   0=code 1=markdown
cell_id:         u32  stable, assigned at creation
execution_count: u32  0 = never executed
source_len:      u32
source:          u8[source_len]
output_count:    u8

  [OUTPUT]  × output_count
  output_type:  u8   0=stdout 1=stderr 2=image_ref 3=error
  output_len:   u32
  output:       u8[output_len]
                  stdout/stderr/error → raw UTF-8
                  image_ref → "{cell_id}/{index}"

Dev Workflow

# First time
cd src/frontend && bun install && cd ../..

# Build everything
bun run build --cwd src/frontend
zig build

# Run (dev mode — assets from disk, no auth)
zig build run -- --dev --no-auth

# In a second terminal, watch the frontend
cd src/frontend && bun run dev

# Tests
zig build test

Notes

Why not embedded CPython?

The initial implementation used translate_c to call CPython directly. That requires matching header versions at compile time. The subprocess approach works with any Python — system, pyenv, conda, uv — and users can switch environments without recompiling.

Why not ZMQ?

stdin/stdout JSON is simpler — no IPC sockets, no connection files, no heartbeat threads. The worker protocol is a single JSON line per command/response, trivial to debug with strace or by hand.

Why not WebSockets?

The execution model is request/response — the browser sends code, the server runs it, the browser re-renders from the response. WebSockets would add complexity without a clear benefit at this stage.

Why .znb and not .ipynb?

The .ipynb JSON format stores binary outputs as base64 and requires parsing the entire document to access a single cell. .znb is compact binary; figures live in the sidecar and are served as static files. .ipynb import/export is planned for Phase 8.

Why sidecar for images?

Keeping artifacts out of the .znb keeps the notebook small. The sidecar is an execution cache — delete it to clear figure outputs. Figures survive server restarts: reopening a notebook shows the last run's plots without re-executing anything.

Single notebook (V1)

Only one notebook is open at a time. The global kernel serves whichever notebook is loaded. Multiple notebooks can run simultaneously by launching multiple server instances on different ports.
